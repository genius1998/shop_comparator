# 트러블슈팅 기록

실제로 발생해 재현하고 고친 문제만 적었다(25건). 날짜가 없는 항목은 모두 2026-10-09~10 작업 중 발생했다. 가장 영향이 컸던 문제는 상품 매칭(T18)이고, 측정 결과는 [matching-evaluation.md](matching-evaluation.md)에 있다.

## T1. 무신사 API가 직접 HTTP 요청에 403을 반환

- **증상**: 옵션·상세 API와 상품 페이지가 모두 403. 본문은 JSON이 아닌 HTML.
- **재현 조건**: `requests`로 Chrome User-Agent, Referer, Origin을 넣어 `goods-detail.musinsa.com/api2/goods/1527076/options`, `api.musinsa.com/api2/dp/v1/goods?goodsNoList=1527076`, `www.musinsa.com/products/1527076` 호출.
- **관측 근거**: 세 요청 모두 `403`, `content-type: text/html`, 길이 5,485바이트의 차단 안내 페이지.
- **원인**: 비브라우저 클라이언트를 엣지에서 거절한다. 로그인 여부와 무관하다.
- **시도한 해결책**: 헤더를 더 붙이는 방식은 시도하지 않았다(브라우저 흉내는 유지보수와 정책 양쪽에서 부적절).
- **최종 수정**: 요청을 무신사 페이지가 열린 Chrome 안에서 `fetch()`로 보낸다(`browser_transport.BrowserSession`). 주문·장바구니 API는 해당 도메인 탭에서 호출한다.
- **검증 결과**: 헤드리스 Chrome에서 같은 옵션 API 200, 재고 API 200, 상세 API 200. 사이즈 7개(225~255) 중 구매 가능 4개(235~250). 웹 작업 `826244640d`로 같은 결과 저장.
- **남은 한계**: 수집할 때마다 Chrome을 띄우므로 작업 시작에 5~20초가 든다. 쇼핑몰이 헤드리스 접근을 막으면 `SHOP_MUSINSA_HEADLESS=0`으로 바꿔야 한다.

## T2. KREAM 상품 페이지와 API가 HTTP 500

- **증상**: `kream.co.kr/products/74130` 과 `api.kream.co.kr/api/p/options/display` 가 500, 본문 0바이트. 이전 작업에서는 사이트 장애나 토큰 만료로 추정했다.
- **재현 조건**: (a) `requests`, (b) Selenium 헤드리스 Chrome, (c) Selenium 일반 창 Chrome(옵션 없음), (d) 일반 브라우저로 같은 주소를 같은 시각에 열었다. 모두 비로그인.
- **관측 근거**

  | 방식 | 문서 응답 | 비고 |
  |---|---|---|
  | (a) requests | 500, 0바이트 | |
  | (b) 헤드리스 Chrome | 500 | 제목이 `kream.co.kr` |
  | (c) 일반 창 Chrome | 200 | `navigator.webdriver = true` 상태 그대로 |
  | (d) 일반 브라우저 | 200 | 상품명, 모델번호 1022A335-001, 사이즈표 표시 |

- **원인**: 헤드리스 브라우저와 비브라우저 클라이언트에 500을 준다. 사이트 장애, 토큰 만료, IP 차단이 아니다.
- **시도한 해결책**: 저장된 토큰 교체는 원인이 아니므로 하지 않았다. 자동화 탐지를 숨기는 옵션(기존 `shop_comparator/shops/kream_login.py`에 있음)도 쓰지 않았다. 필요하지 않았기 때문이다.
- **최종 수정**: KREAM용 Chrome은 헤드리스로 띄우지 않는다(`browser_transport.headless_default`). 작업 중에는 창을 최소화한다.
- **검증 결과**: 일반 창에서 문서 200. 이후 KREAM 시세 수집·세션 확인·거래량 필터를 모두 최소화된 일반 창으로 실행해 성공.
- **남은 한계**: KREAM 작업 중 Chrome 창이 작업 표시줄에 나타난다. KREAM이 자동화 브라우저 전체를 거절하게 되면 동작하지 않는다.

## T3. KREAM 자동 로그인이 입력란을 찾지 못함

- **증상**: 기존 `kream_login.login_and_save_kream_cookies`가 로그인 페이지에서 20초 대기 후 실패.
- **재현 조건**: `https://kream.co.kr/login` 을 열고 `input` 요소를 센다.
- **관측 근거**: `/login` 의 `input` 0개. 버튼은 "네이버로 로그인", "Apple로 로그인", "휴대폰으로 로그인"과 "이메일 로그인" 링크(`/login/email`). `/login/email` 에는 `input[type=email]`(placeholder `abc@email.co.kr`), `input[type=password]`, 오류 표시용 `.input_error`.
- **원인**: KREAM이 로그인 첫 화면을 간편 로그인 선택 화면으로 바꾸고 이메일 로그인을 하위 경로로 옮겼다.
- **최종 수정**: `site_login.login_kream`이 `/login/email` 로 바로 이동해 입력하고 Enter로 제출한다. 네이버·Apple 계정용으로 [창에서 직접 로그인]을 남겼다.
- **검증 결과**: 입력란 탐지는 실제 페이지로 확인. 계정 자동 입력 후 제출은 실계정으로 실행하지 않았다(사용자가 창에서 직접 로그인). 로그인된 프로필의 인증은 체결 내역 API 200으로 확인.
- **남은 한계**: 화면 구조가 다시 바뀌면 "로그인 입력란을 찾지 못했습니다" 오류가 나고 수동 로그인으로 우회해야 한다.

## T4. 저장된 무신사 세션이 주문서 조회에서 401

- **증상**: 로그인 쿠키가 저장되어 있는데 회원가 조회가 401로 실패.
- **재현 조건**: 로그인하지 않은(또는 만료된) 상태에서 `order.musinsa.com/api2/order/v1/orders/order-form` 호출.
- **관측 근거**: 웹 작업 `003a1c5cd1` 로그 — "주문서 API가 인증을 거절했습니다 (HTTP 401)". 같은 프로필에서 옵션·재고 API는 200.
- **원인**: 공개 API는 세션 없이 응답하고 주문서 API만 회원 세션을 요구한다. 이전 구현은 쿠키가 존재하는지만 보고 로그인된 것으로 취급했고, 쿠키를 파일에서 새 브라우저로 주입하는 방식이라 만료를 알 수 없었다.
- **최종 수정**: (1) 쇼핑몰별 전용 Chrome 프로필을 쓰고, 무신사는 저장한 로그인 쿠키를 작업마다 다시 넣는다(T12). (2) 로그인 직후와 회원가 수집 시작 때마다 주문서 API로 인증을 확인한다. (3) 401이면 요청을 더 보내지 않고 "로그인 필요"로 끝낸다.
- **검증 결과**: 비로그인 상태에서 회원가 수집이 장바구니 요청 전에 `auth` 오류로 끝나는 것을 실사이트로 확인. 재고만 수집하는 모드는 같은 상태에서 정상 동작. 로그인 후에는 T12를 추가로 고친 뒤 회원가 수집 성공.
- **남은 한계**: 세션 유효 기간은 쇼핑몰이 정한다. 만료되면 다시 로그인해야 한다.

## T5. 테스트 실행이 사용자의 검색 제외 CSV를 다시 썼음

- **증상**: 테스트 실행 뒤 `git status`에 추적 파일 `kream_search_blacklist.csv`가 수정됨으로 나타남(204줄 변경, 내용은 같고 순서만 정렬됨).
- **재현 조건**: `tests/test_web_app.py`의 수동 매칭 테스트가 `POST /api/matches`를 호출 → `pipeline.blacklist_remove`가 실제 프로젝트 폴더의 CSV를 읽어 정렬한 뒤 다시 저장.
- **관측 근거**: `git diff --stat kream_search_blacklist.csv` → `408 +++---`.
- **원인**: 테스트가 DB만 임시 파일로 바꾸고 CSV 경로는 바꾸지 않았다. 또 제거할 항목이 없어도 파일을 다시 쓰는 구현이었다.
- **최종 수정**: 파일을 `git checkout`으로 되돌렸다. `TempDbTestCase`가 제외 목록 경로를 임시 폴더로 바꾸게 했고, `blacklist_remove`는 실제로 지울 행이 있을 때만 원래 순서를 유지한 채 저장한다.
- **검증 결과**: 전체 테스트를 다시 돌린 뒤 `git status`에서 해당 파일 변경 없음.
- **남은 한계**: 없음.

## T6. 작업 오류 문구에 비밀번호가 남을 수 있었음

- **증상**: 로그인 함수가 오류 문구에 비밀번호를 넣어 예외를 던지는 경우, 로그는 마스킹되지만 `/api/state`의 작업 오류와 `job_runs` 테이블에는 원문이 저장됨.
- **재현 조건**: 회귀 테스트 `test_password_never_appears_in_state_logs_or_database`(일부러 비밀번호를 로그와 예외에 넣는 가짜 로그인 함수 사용).
- **관측 근거**: 테스트 실패 출력의 `"error": "무신사: 로그인 실패 (<비밀번호>)"`.
- **원인**: 마스킹을 로그 기록 경로에만 적용하고 작업 상태 저장 경로에는 적용하지 않았다.
- **최종 수정**: `JobManager`가 오류 문구를 `redact()`한 뒤 저장한다.
- **검증 결과**: 같은 테스트 통과. 상태 API, 로그 API, 작업 이력, DB 파일 바이트에서 비밀번호가 발견되지 않음.
- **남은 한계**: 실제 로그인 코드는 오류 문구에 비밀번호를 넣지 않는다. 이 수정은 방어 계층이다.

## T7. 입찰 엑셀의 판매 희망가가 1,000원 높게 계산됨

- **증상**: 회원가 90,000원, 마진율 10%에서 판매 희망가가 99,000원이 아니라 100,000원.
- **재현 조건**: 테스트 `test_bid_sheet_uses_each_sizes_own_price_and_only_matched_sizes`. GUI의 `_generate_excel_task`와 같은 식 `ceil(price * (1 + rate) / 1000) * 1000`.
- **관측 근거**: `90000 * 1.1 = 99000.00000000001` → 올림하면 100,000.
- **원인**: 부동소수점 오차가 1,000원 단위 올림과 만나 한 단계 위로 넘어간다.
- **최종 수정**: `exports.bid_rows`가 `Decimal`로 계산한다.
- **검증 결과**: 같은 테스트에서 99,000원, 95,000원 → 105,000원.
- **남은 한계**: 데스크톱 GUI의 엑셀 생성은 수정하지 않았다(같은 오차가 남아 있다).

## T8. 상태 조회가 서버 CPU를 점유해 화면이 느려짐

- **증상**: 상품 목록 API 7~8초, 상태 API 2~4초. 매칭 탭이 3.5초 안에 그려지지 않음.
- **재현 조건**: 브라우저 탭 두 개가 2초마다 `/api/state`를 호출하는 상태에서 다른 API 호출.
- **관측 근거**: 같은 코드를 새 포트에 띄우면 상품 API 1.05초, 상태 API 0.47초. 운영 중인 서버 프로세스의 누적 CPU 134초. 프로파일에서 상태 API가 상품·사이즈·매칭 전체 행을 매번 읽고, 매칭 조회가 큰 텍스트 열까지 가져옴.
- **원인**: 2초 주기의 상태 폴링이 요청당 0.5초의 CPU를 써서 다른 요청이 밀렸다.
- **최종 수정**: 상태 API는 `COUNT` 쿼리만 쓴다(`store.counts`). 매칭 조회에서 큰 텍스트 열을 제외했다. 화면이 보이지 않을 때는 폴링을 10초로 늦춘다.
- **검증 결과**: 상태 API 0.04~0.05초, 상품 API 0.7초, 매칭 API 0.33초(상품 103개 기준).
- **남은 한계**: 상품이 수천 개가 되면 상품 API를 페이지 단위로 나눠야 한다.

## T9. Windows에서 테스트 임시 DB를 지우지 못함

- **증상**: 테스트 21개 중 17개가 `PermissionError: [WinError 32]`로 실패.
- **재현 조건**: 임시 폴더의 SQLite 파일을 연 채로 `TemporaryDirectory.cleanup()` 호출.
- **원인**: `with database.get_db_conn() as conn` 은 커밋만 하고 연결을 닫지 않는다. Windows는 열린 파일을 지울 수 없다.
- **최종 수정**: 테스트 헬퍼가 연 연결을 모아 두었다가 정리 단계에서 닫는다.
- **검증 결과**: 전체 테스트 통과.
- **남은 한계**: 앱 코드의 연결은 기존 방식대로 가비지 컬렉션에 맡긴다.

## T10. KREAM API 요청이 브라우저 안에서 "Failed to fetch"

- **증상**: KREAM 페이지 안에서 `api.kream.co.kr`로 보낸 `fetch()`가 응답 없이 실패.
- **재현 조건**: 일반 창 Chrome의 `kream.co.kr` 페이지에서 `fetch(url, {credentials: 'include'})`.
- **관측 근거**: Chrome 네트워크 로그 — 사전 요청(Preflight) 200, 본 요청 `net::ERR_FAILED`, `corsError: PreflightInvalidAllowCredentials`. 헤더 구성을 바꿔도 같음.
- **원인**: KREAM API의 CORS 응답은 쿠키 포함 요청을 허용하지 않는다. KREAM 화면은 쿠키가 아니라 `Authorization` 헤더로 인증한다. 이전 웹 구현은 모든 요청에 `credentials: 'include'`를 썼으므로, 로그인이 유효했더라도 KREAM 호출은 모두 실패했을 것이다.
- **최종 수정**: `api.kream.co.kr` 요청만 `credentials: 'omit'`으로 보낸다(`browser_transport.BrowserSession.request`).
- **검증 결과**: 같은 요청이 API까지 도달(다음 항목의 403 → 수정 후 200).
- **남은 한계**: 없음.

## T11. KREAM API가 403 (본문 없음)

- **증상**: T10 수정 뒤 시세·검색·체결 API가 모두 403, 본문 0바이트.
- **재현 조건**: 코드 상수의 헤더(`x-kream-api-version: 52`, `x-kream-web-build-version: 25.15.7`, 저장된 기기 ID)로 호출.
- **관측 근거**: KREAM 화면이 직접 보내는 요청은 같은 시각에 200. 그 요청의 헤더는 API 버전 `64`, 빌드 버전 `26.13.5`, 기기 ID는 `web;` + `webDid` 쿠키 값. 관측한 헤더로 다시 보내면 시세 200(413KB), 검색 200, 체결 내역 401(`Access token not found!`).
- **원인**: 오래된 버전·기기 ID 헤더를 거절한다. 상품 페이지는 서버 렌더링이라 열기만 해서는 API 요청이 발생하지 않아, "실제 요청에서 관측한 값을 우선"하는 기존 보완책이 관측할 요청 자체가 없었다.
- **시도한 해결책**: 화면의 SHOP 링크를 눌러 요청을 발생시키고 관측하는 방법으로 값은 확인했으나, 매번 화면을 조작해야 해서 채택하지 않았다.
- **최종 수정**: 페이지에 들어 있는 사이트 자체 설정(`__NUXT__.config`의 `apiVersion`, `buildVersion`, `webRequestSecret`)과 `webDid` 쿠키를 읽어 헤더를 만든다(`BrowserSession._read_kream_config`). 실제 요청을 관측하면 그 값이 우선한다.
- **검증 결과**: 로그인 없이 KREAM 74130 사이즈 17개, KREAM 36 사이즈 18개의 시세 수집 성공. 이 과정에서 시세와 검색은 로그인이 필요 없는 공개 API이고 체결 내역만 로그인이 필요하다는 것을 확인해, 매칭·가격 수집에서 로그인 요구를 없앴다.
- **남은 한계**: KREAM이 설정 위치나 이름을 바꾸면 다시 403이 난다. 그때는 `schema`가 아니라 `blocked`로 보이므로 이 항목을 먼저 의심해야 한다.

- **최종 수정**: 네트워크 오류는 5초 뒤 한 번 재시도하고, 3회 연속 실패하면 작업을 멈춘다. 인증·차단·한도 오류는 재시도하지 않는다.
- **검증 결과**: 회귀 테스트 `test_dropped_connection_is_retried_once_then_stops_instead_of_racing_through`. 상위 200개 실행에서 4건이 재시도로 복구되어 130개 전부 수집.
- **남은 한계**: 긴 장애에서는 작업이 멈추고 사용자가 다시 시작해야 한다.

## T21. 브랜드 배송 상품에서 400과 내부 번호 사이즈

- **증상**: 일부 KREAM 상품에서 판매 쪽 API가 400을 반환하고, 사이즈가 `761962` 같은 번호로 저장됨.
- **재현 조건**: 상품 유형이 `product_brand`(브랜드가 직접 배송)인 상품.
- **관측 근거**: 구매 쪽 응답의 `option_key`가 내부 옵션 번호이고 화면 표시용 사이즈는 `option_name_display`에 따로 있다. 판매 쪽은 400.
- **원인**: 브랜드 배송 상품은 개인이 판매할 수 없어 판매 쪽이 없다. 옵션 키가 사이즈 문자열이라는 가정이 틀렸다.
- **최종 수정**: 판매 쪽 400은 "즉시판매가 없음"으로 처리하고 구매 가격은 저장한다. 사이즈는 표시 이름으로 바꿔 저장한다(`kream_api.option_names`).
- **검증 결과**: 회귀 테스트 `test_brand_shipped_product_uses_displayed_size_not_option_id`. 실제 상품 재수집에서 사이즈가 `240` 형태로 저장됨.
- **남은 한계**: 없음.

## T22. 체결 내역 API가 429

- **증상**: 거래량 필터 실행 중 30개 상품 뒤부터 429.

- **원인**: 체결 내역 API의 요청 한도가 시세 API보다 낮다.
- **최종 수정**: 429에서 즉시 중단한다. 요청 간격을 3초 이상으로 늘렸다. 우회하지 않는다.

## T23. 수집 중 Chrome 창이 계속 앞으로 나와 작업을 방해

- **증상**: KREAM 수집 중 Chrome 창이 요청마다 포커스를 가져감(사용자 보고).
- **재현 조건**: KREAM은 헤드리스가 거절되어(T2) 일반 창으로 실행한다.
- **원인**: 요청을 보낼 때마다 Selenium의 `switch_to.window`를 호출했고, Windows에서 이 호출이 창을 앞으로 가져온다.
- **최종 수정**: 탭이 실제로 바뀔 때만 전환한다. 창을 화면 밖 좌표에 띄우고, 창을 연 직후 원래 창으로 포커스를 되돌린다.
- **검증 결과**: 이후 200개 수집 동안 포커스 이동이 보고되지 않음.
- **남은 한계**: 로그인 창은 사용자가 조작해야 하므로 화면에 띄운다.

## T25. 패키지 구조로 옮기면 조용히 깨지는 경로 2곳

- **증상**: 루트에 평면으로 있던 모듈 37개를 `shop_comparator/` 패키지로 옮긴 뒤에도 테스트는 전부 통과했지만, 실행 환경에서만 드러나는 경로 의존이 2곳 있었다.
- **관측 근거**: (1) `product_matcher.load_local_env`가 `.env`를 "자기 파일 옆"에서 찾았다. 옮기면 `.env`를 못 찾고 오류 없이 지나가, 로그인 버튼과 OpenAI 키가 사라진다. (2) `crawler`가 품번 조회를 `python musinsa_serial.py`라는 상대 파일명으로 실행했다.
- **원인**: 파일 위치를 기준으로 한 경로와 스크립트 이름 호출.
- **최종 수정**: `.env`는 프로젝트 루트에서 찾고, 보조 스크립트는 `python -m shop_comparator.shops.musinsa_serial`로 실행한다. import는 AST로 172곳을 일괄 변환했고, 테스트의 `mock.patch("모듈.이름")` 문자열도 함께 바꿨다.
- **검증 결과**: 전체 모듈 import 검사(실패 0), 테스트 전체 통과, 서버 재시작 후 상태 API·화면·기존 수집 결과 확인.
- **남은 한계**: 런타임 데이터(DB, 쿠키, 로그)는 실행 폴더 기준 경로를 그대로 쓴다. 프로젝트 루트에서 실행해야 한다.
